# Benchmark reproducibility

How to reproduce dorian's benchmarks, and what a reproduction does (and does not)
establish. The standard this project holds itself to: **a benchmark is evidence
only if a skeptic can clone the named inputs at the named SHAs, run the named
commands, and get the same numbers.** See [VALIDATION_HONESTY.md](VALIDATION_HONESTY.md)
for what those numbers mean.

## The benchmarks and how to run them

| Benchmark | Command | Inputs | What it measures |
|---|---|---|---|
| Controlled mutation (v0.7.0) | `dorian bench large-mutation` | invented synthetic fixtures | trigger/selection vs. a baseline watcher, on a designed distribution |
| Earlier/smaller mutation | `dorian bench mutation` | invented synthetic fixtures | the first, smaller version of the above |
| Binding lifecycle | `dorian bench binding-lifecycle` (`--quick` for a CI subset) | invented synthetic fixtures | symbol-binding selection recall (trigger) and alarm precision (truth), reported separately |
| Real-world use cases | `dorian bench realworld-usecases` | offline reproductions of public problem *classes* | that a public problem class reproduces — not a blanket real-world result |
| Extraction churn | `dorian bench churn` | synthetic documents | `--extract` stability (frozen/experimental) |
| Public micro-benchmark | _protocol only_ — see [PUBLIC_BENCHMARK_PROTOCOL.md](PUBLIC_BENCHMARK_PROTOCOL.md) | real public repos at frozen SHAs (`bench/public/repos.public.json`) | hermetic reproduction on real inputs, when run |

## What makes them reproducible

- **Determinism.** Sidecars are content-addressed; `report --audit` is
  byte-identical across runs; the seal pipeline does not depend on wall-clock or
  randomness for its verdicts. Two runs of the same benchmark on the same inputs
  produce the same numbers.
- **Frozen inputs.** Synthetic fixtures are generated by committed code; the
  public manifest pins exact SHAs and licenses.
- **No model at check time.** Verdicts come from deterministic checkers, not an
  LLM, so they do not drift between runs or model versions.

## What a reproduction establishes

- **Yes:** the mechanism is deterministic and inspectable; on *these* inputs the
  reported trigger/truth numbers hold; the process can be independently re-run.
- **No:** the numbers transfer to your repo; dorian is "validated"; synthetic
  performance predicts real-world performance. Hermetic reproduction is not broad
  validation.

## Reporting rules for a new benchmark

1. Separate **trigger/selection** metrics from **truth/alarm** metrics; never
   report a single blended score.
2. Label synthetic inputs as synthetic, in the result doc's first paragraph.
3. State the baseline and the exact inputs; a delta without a baseline is not a
   result.
4. Commit the protocol before the results when the design has any freedom that
   could be tuned to flatter the outcome (pre-registration).
5. No forbidden words (proven, validated, production-ready, semantic proof,
   "works on real repos") except inside an explicit forbidden-words list.

## Environment

- Python 3.11+ (CI matrix: 3.11 / 3.12 / 3.13).
- `uv sync` for the dev environment; benchmarks run via `dorian bench …` or the
  `make bench*` targets.
- The public micro-benchmark additionally needs network access to clone the
  pinned repos (one-time) — it is otherwise offline.
